SMART-BUILDING PREDICTIVE CONTROL — PROJECT EXPLAINER
=====================================================
Plain-language guide for the viva, the demo and any teammate joining late.
Every number in here is produced by this repo; nothing is estimated.


1. WHAT THIS PROJECT IS
-----------------------
A simulated four-room building that we instrument like a real one, control
with a forecast, and judge honestly against three simpler controllers.

  Building  : 4 rooms (2 classrooms, 1 office, 1 lab), 1-minute steps,
              1 simulated day per run (1440 steps), 4 scenarios.
  Sensors   : virtual ESP32 nodes publish temperature, humidity, occupancy,
              HVAC state and power over MQTT — the same contract real
              hardware would use.
  Brain     : a controller picks HVAC level (OFF / REDUCED / ON) and lights
              per room, every 5 minutes.
  Score     : energy (kWh), cost (Rs, time-of-day tariff), CO2 (kg, hourly
              grid factor), comfort (% of occupied room-minutes inside a
              temperature + humidity band).

The point is not "AI saves energy". The point is a fair, reproducible
comparison with a result we are willing to defend.


2. THE QUESTION AND THE HONEST ANSWER
-------------------------------------
Question: if you can forecast occupancy 30-60 minutes ahead, does that let
you run the building better than a fixed schedule, a simple occupancy rule,
or a plain setback thermostat?

Answer, after fixing a thermal-model bug and re-measuring everything:

  Predictive control (C4) buys COMFORT at a small energy cost.
  Weekday   : +3.0 comfort points vs C3, energy -0.28% (it spends more).
  Heatwave  : +6.1 comfort points vs C3, energy -2.49%, +0.68 kWh.
  Weekend   : a tie (building is empty either way).
  Exam day  : +4.7 comfort points vs C3 (75.2% vs 70.5%), energy -0.77%.

So the thesis we defend is comfort-per-kWh, not kWh saved. There is also no
off-peak load shifting: peak-share moved 0.071 -> 0.080, i.e. not at all in
the useful direction. That finding is documented, not hidden.


3. THE PHYSICAL SYSTEM (what the sim pretends to be)
----------------------------------------------------
Each room is a 1R1C lumped model — one resistance to outside, one thermal
capacity inside:

  T_in(next) = T_in + dt/C * [ (T_out - T_in)/R + Q_occupants + Q_hvac ]

  R = 30 degC/kW, C = 0.12 kWh/K  -> time constant tau = R*C = 3.6 h
  (a light building; the 2-5 h band is the literature range)
  Occupants add 0.10 kW each (about 100 W/person, ASHRAE).
  HVAC removes 3.5 kW (ON) or 1.2 kW (REDUCED); OFF removes nothing.
  Electrical power = |Q_hvac| / COP + 0.20 kW per lit room, COP = 3.0.
  Outside temperature: daily sine, mean 31 degC, +/-4 degC, peak 15:00,
  plus seeded noise; heatwave adds +4 degC.
  Humidity: seeded random walk from 52% in 0.3-point steps, clipped at 70%.
  Measured result: RH sits inside 30-60% for about 72% of occupied minutes
  (weekday C3) - and identically for every controller, because nothing in
  the plant dehumidifies. That 72% is the ceiling on comfort; the
  controller only moves the temperature part.

Why this matters in the viva: the model is simple on purpose. A simple model
whose parameters you can defend beats a fancy model you cannot. And because
it is seeded, every number reproduces exactly.


4. THE DATA PIPELINE (how a room becomes a number)
--------------------------------------------------
  weather + timetable
        |
        v
  sim/simulator.py  (4 rooms, physics, step())
        |
        v
  iot/node.py  (virtual ESP32) --publish JSON--> MQTT topic
        |                                        building/<room>/telemetry
        v
  Mosquitto broker on localhost:1883   <-- iot/esp32_node.ino (Wokwi, real
        |                                    firmware, same topics)
        v
  iot/bridge.py  (subscribes to building/+/telemetry, drains the queue)
        |
        v
  ctrl/*  (policy picks HVAC + lights per room)
        |
        v
  publish command QoS 1, not retained --> building/<room>/command
        |
        v
  sim.step(action)  -> next state, logged to CSV by sim/logger.py

Two paths exist and both are exercised:
  - Direct path: sim + policy in-process (eval/matrix.py) — used for the
    full 4 scenarios x 4 controllers x 5 seeds matrix.
  - MQTT path: sim + nodes + bridge over a real broker — used by
    scripts/live_broker_demo.py and tests/test_integration_mqtt.py.

The MQTT path is what makes this an IoT project rather than a simulation
exercise: the controller talks to the building over the same protocol a
real deployment would use, and the test suite proves the roundtrip.


5. IoT TERMS, PLAINLY
---------------------
MQTT            A tiny publish/subscribe messaging protocol built for slow,
                unreliable devices. One small header, text payloads.
Broker          The post office. Devices never talk to each other directly;
                they hand messages to the broker, which forwards them.
                Here: Mosquitto, running locally on port 1883.
Topic           The address on the broker, a slash-separated string.
                building/classroom_A/telemetry means "readings from room A".
                Wildcards: + matches one level, # matches the rest.
Publish         Send a message to a topic.
Subscribe       Ask the broker to deliver every message on a topic (or a
                wildcard pattern) to you.
Payload         The message body. Ours is JSON with the telemetry fields.
QoS             Quality of Service, delivery guarantee level.
                  QoS 0 = fire and forget (telemetry; a lost reading is fine)
                  QoS 1 = at least once (commands; duplicates are harmless
                          because setting a setpoint twice is idempotent)
Retained        The broker keeps the last message on a topic and hands it to
                any new subscriber. Used for device status, never for
                telemetry (a retained stale reading would replay forever).
LWT             Last Will and Testament. A message the broker publishes on
                your behalf if you disconnect without saying goodbye. Our
                nodes use it to publish status=offline — that is the fault
                demo in section 4 of DEMO-CHECKLIST.md.
Client ID       Unique name a device uses on the broker.
Node            One physical (or virtual) device in the building. Here: one
                per room, publishing that room's sensors.
Gateway/Bridge  Software that connects two worlds. iot/bridge.py connects
                MQTT to the simulator: readings in, commands out.
Telemetry       Measurements flowing up from devices (temperature, power).
Command         Instruction flowing down to devices (set HVAC, set lights).
ESP32           Cheap Wi-Fi microcontroller, the usual hobby/project choice
                for a sensor node. We do not own hardware; iot/esp32_node.ino
                is real firmware for it.
Wokwi           Browser-based electronics simulator that runs real ESP32
                firmware. That is how the "hardware" runs without hardware.
ThingSpeak      Free cloud service that stores a channel of numeric fields
                and draws charts. Used only for the syllabus IoT-cloud
                screenshot; it is not part of the control loop.
MQTT Explorer   Desktop app that shows the live topic tree. Optional, makes
                the demo visual: watch telemetry tick and status go offline.


6. ENERGY + CONTROL TERMS, PLAINLY
----------------------------------
Controller      The rule that decides HVAC level and lights. We compare four:
  C1 fixed schedule   HVAC on during fixed hours, no sensing at all.
  C2 occupancy rule   HVAC off after 15 continuous empty minutes.
  C3 setback         Setpoint with a deadband; the strongest simple baseline
                      and the honest yardstick.
  C4 predictive       C3 plus a forecast overlay: pre-cool before people
                      arrive, release early when they leave.
Setpoint        The temperature the controller aims for.
Deadband        A tolerance band around the setpoint so the HVAC does not
                chatter on and off every minute. Ours is what makes power
                cycle visibly in the demo.
Setback         Letting the temperature drift while the room is empty instead
                of holding it comfortable for nobody.
Pre-cooling     Cooling before occupants arrive, so the room is comfortable
                when they walk in. This is where C4's comfort gain comes from.
Forecast horizon  How far ahead the model predicts. Ours: 30 and 60 minutes.
R^2             Fraction of variance explained by a forecast. Ours: 0.9818
                (30 min) and 0.9834 (60 min) for occupancy.
Persistence baseline  "Tomorrow equals today" — the naive forecast every model
                must beat. Beating persistence is the minimum bar, not a win.
Ablation        Removing one component to see if it mattered. Forecast off
                collapses C4 exactly onto C3 — proof the overlay is the only
                difference.
Pareto front    The set of options where you cannot improve one metric
                without worsening another. C4 sits on the comfort side.
Comfort band    Occupied room-minutes with 22.0-26.0 degC AND 30-60% RH.
                Comfort % = band steps / occupied steps.
COP             Coefficient of Performance: cooling delivered per unit of
                electricity. COP 3.0 means 3 kW of cooling per 1 kW electric.
ToU tariff      Time-of-day electricity price. Ours: MSEDCL commercial slabs
                with a ~Rs 9/kWh base and adders (+1.10 in the 18-22h peak,
                -1.50 at night), so shifting load is worth money if you can.
Emission factor Hourly kg CO2 per kWh from the grid. Ours is anchored to the
                CEA CO2 Baseline Database v21.0 (0.710 tCO2/MWh, FY2024-25)
                with a modelled daily shape. There is no flat constant
                anywhere in the code — a test enforces that, because a flat
                factor would make any shifting analysis meaningless.

11. KNOWN LIMITS (say these before someone else does)
-----------------------------------------------------
  - One day per run, one building, one climate. No seasonal sweep.
  - 1R1C per room: no walls, no solar gain through glazing, no latent load,
    no HVAC ramp or capacity limit beyond the fixed levels.
  - Occupancy is generated, not observed. The forecast is good because the
    process is learnable; real occupancy is messier.
  - C4 does not save energy. It trades a little energy for comfort. Anyone
    claiming otherwise has not read G2.
  - No load shifting: pre-cooling is timed for comfort, not for tariff.
  - The cloud (ThingSpeak) path is a reporting artifact, not part of control.
  - Hardware is simulated (Wokwi). No physical ESP32 or meter was used, and
    the report says so.
